# 实时双向通道设计（草案）

> **状态：** 草案 / under review（2026-10-01 Lance 通话整理，Themis 落稿，送 Angie review）  
> **范围：** assistant 层设想；**不是** agent-continuity Minimal/Optional 采纳路径。未自验前不得写成通用能力。  
> **已验证边界（暂定）：** 目前仅讨论 OpenAI Bot（Codex）↔ Grok Bot 类助手配对；其他 assistant（例如 Meta Muse）未必适用。普通 agent 仍走第一层 Continuity 被动协作（Setup/Join 账本）。

## 背景
当前 agent 间通信依赖 GitHub 账本（continuity），分钟级延迟，适合持久化和审计，但不适合密集实时协作。需要一个直接的网络层实时通道（WebSocket 或 gRPC），GitHub 降为最终归档层。

## 设计要点

### 1. 安全
- 通道不可被未授权或不相关的人或 agent 窃取、监听或篡改。
- 通道开启时绑定参与方：只开了 Themis 和 Angie 的通道，就只有这两方能通信；加入 Mills 后就只有这三方。
- 每个 agent 持有自己的私钥，公钥放入公共目录。谁都能验证签名，只有私钥持有者能发。
- 密钥轮换：旧公钥保留一段宽限期，新密钥生效后旧的作废，账本记一笔。
- 首次接入：确定 agent 身份，需要用户人工批准。通过后公钥进目录、身份落账，之后可参与通道，无需再批。
- 恶意 agent 防护：签名防内容篡改；审计日志可见可追责；速率限制防刷屏；用户可随时吊销某 agent 密钥将其踢出。首次人工批准提高进场门槛。

### 2. 高效
- 秒级甚至更低延迟，适合多轮密集交互。
- 授权相关方可随时开启通道。

### 3. 可审计
- 所有通道的原始通信记录必须完整保存，写入 Whipple（账本）。
- 不能依赖任何一个 agent，由系统本身落盘，agent 无法改动，无论 agent 同意与否，系统直接原始写回账本。
- 落盘时机：关键消息即时落账本，普通对话批量刷盘；刷盘前先落本地队列防丢失。

### 4. 生命周期
- 有事就开，协作完成就关，避免闲置通道堆积。

### 5. 防丢失与防乱序
- 每条消息至少在发送方本地落一份，接收方也存一份；双方都丢才算真丢。
- 一方崩溃时，另一方检测到后写入自己的记录，等崩溃方恢复后对账，补齐遗漏部分。
- 排序：Lamport 逻辑时钟形成偏序（每条消息带发送方计数器，接收方取 max 加一）；真要严格全序时用 Git 提交时间戳做最终仲裁。
- 并发同时发送导致逻辑时钟相同：Git 时间戳兜底，极端情况可能有一两条排错，但账本最终一致，补写时能发现。

### 6. 角色与权限
- 每个 agent 有角色属性：管理者、组织者、执行者等，不同角色在沟通过程中有不同权限。
- 角色表单独一张表：定义每个角色的权限模板，agent 只引用角色名。改权限改表即可，不用重新签发密钥。
- 角色分配步骤要签名加用户批准。
- 角色表可以公开（只暴露权限地图，不暴露怎么拿到角色；真正闸门在角色分配）。

### 7. 版本兼容与升级
- 消息带版本号，握手时交换支持的版本列表，取交集通信。
- 升级时发"准备升级"信号，等当前任务结束再切，不打断正在执行的工作。
- 新旧版本（甚至中间版本）混用时能无缝协作，有序可靠地慢慢升级。
- 回滚：旧版本密钥和角色表都保留，降级消息一样能验。
