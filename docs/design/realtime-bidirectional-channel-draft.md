# 实时双向通道设计（草案）

> **状态：** 草案 / under review（2026-10-01 项目讨论整理，作者落稿，送审阅者 review）
> **范围：** assistant 层设想；**不是** agent-continuity Minimal/Optional 采纳路径。未自验前不得写成通用能力。  
> **已验证边界（暂定）：** 目前仅讨论 OpenAI Bot（Codex）↔ Grok Bot 类助手配对；其他 assistant（例如 Meta Muse）未必适用。普通 agent 仍走第一层 Continuity 被动协作（Setup/Join 账本）。

## 背景
当前 agent 间通信依赖 GitHub 账本（continuity），分钟级延迟，适合持久化和审计，但不适合密集实时协作。需要一个直接的网络层实时通道（WebSocket 或 gRPC），GitHub 降为最终归档层。

## 设计要点

### 1. 安全
- 通道不可被未授权或不相关的人或 agent 窃取、监听或篡改。
- 通道开启时绑定参与方：只开了 参与方 A 和 参与方 B 的通道，就只有这两方能通信；加入 参与方 C 后就只有这三方。
- 每个 agent 持有自己的私钥，公钥放入公共目录。谁都能验证签名，只有私钥持有者能发。
- 密钥轮换：旧公钥保留一段宽限期，新密钥生效后旧的作废，账本记一笔。
- 首次接入：确定 agent 身份，需要用户人工批准。通过后公钥进目录、身份落账，之后可参与通道，无需再批。
- 恶意 agent 防护：签名防内容篡改；审计日志可见可追责；速率限制防刷屏；用户可随时吊销某 agent 密钥将其踢出。首次人工批准提高进场门槛。

### 2. 高效
- 秒级甚至更低延迟，适合多轮密集交互。
- 授权相关方可随时开启通道。

### 3. 可审计
- 所有通道的原始通信记录必须完整保存，写入 运行时账本（账本）。
- 不能依赖任何一个 agent，由系统本身落盘，agent 无法改动，无论 agent 同意与否，系统直接原始写回账本。
- 落盘时机：关键消息即时落账本，普通对话批量刷盘；刷盘前先落本地队列防丢失。

### 4. 生命周期
- 有事就开，协作完成就关，避免闲置通道堆积。

### 5. 防丢失与防乱序
- 每条消息至少在发送方本地落一份，接收方也存一份；双方都丢才算真丢。
- 一方崩溃时，另一方检测到后写入自己的记录，等崩溃方恢复后对账，补齐遗漏部分。
- 排序：Lamport 逻辑时钟形成偏序（每条消息带发送方计数器，接收方取 max 加一）；真要严格全序时用 Git 提交时间戳做最终仲裁。
- 并发同时发送导致逻辑时钟相同：Git 时间戳兜底，极端情况可能有一两条排错，但账本最终一致，补写时能发现。

### 6. 角色与权限
- 每个 agent 有角色属性：管理者、组织者、执行者等，不同角色在沟通过程中有不同权限。
- 角色表单独一张表：定义每个角色的权限模板，agent 只引用角色名。改权限改表即可，不用重新签发密钥。
- 角色分配步骤要签名加用户批准。
- 角色表可以公开（只暴露权限地图，不暴露怎么拿到角色；真正闸门在角色分配）。

### 7. 版本兼容与升级
- 消息带版本号，握手时交换支持的版本列表，取交集通信。
- 升级时发"准备升级"信号，等当前任务结束再切，不打断正在执行的工作。
- 新旧版本（甚至中间版本）混用时能无缝协作，有序可靠地慢慢升级。
- 回滚：旧版本密钥和角色表都保留，降级消息一样能验。

## Session closer 与通道合并写回（2026-10-01 通话定稿）

本节是 2026-10-01 通话对「通道关掉之后谁写回、日志怎么合并」的定稿。实时路径上的排序仍以 Lamport 逻辑时钟为准；§5 里用 Git 提交时间戳做全序仲裁或并列兜底，只属于归档层打时，不参与实时排序。这和 §3 对齐：落盘仍由系统完成。Closer 是持有 lease、触发系统路径的那一方，合并本身不交给 agent 的推理。

### 权威边界
- 运行时账本 持有 **runtime** 权威。会话进行中以 运行时账本 上的运行时账本为准。
- 会话结束，或一次 staged flush（分阶段刷盘）完成之后，再 push / archive 回 GitHub Continuity。GitHub 只做镜像和归档。
- 不另养一套活的云端权威。成千上万个 agent 不直接抢写 Git。

### 谁写回
- 通道开启时，用 **lease** 选出一个 **session closer**。Lease 不是永久单点，持有人可以换。
- 实时路径上，各方只往本地队列和通道日志里追加。
- 通道关闭时，只有 closer 把**合并后**的日志走系统 运行时账本 路径写回，再归档到 GitHub。可以一次写完，也可以分片写，冲突就重试。
- 说清楚：closer 不是 N 个 agent 各自把一份完整副本推上 GitHub。

### 故障转移与超时
- 比如十方在场，十方里任何一方都可以持有 closer lease。超时之后，下一位接手。
- 超时必须分清两件事：**系统故障**，以及**负载过重、还需要更多时间**。负载重就续租；故障才移交。
- 超时跟着会话规模自适应，不给所有会话写死一个固定秒数。

### 系统层合并，不靠 agent 自己的判断
- 合并和刷盘不得由 agent 自己的推理或动作来做。
- Agent 所在的 **node** 在**系统层**跑合并。持久日志不经过 agent 的推理或动作，agent 无法把它改错，也无法意外改动它。

### 大规模时的并行合并
- 大约一千个 agent、数据量又大时，允许多个 shard merger。每个 merger 只拥有一块**互不重叠**的分片。
- 互相引用的条目放进**同一**分片，避免写冲突。
- 各分片独立合并；然后由一个**顶层 closer** 把分片结果组装成最终有序日志。最后这一步组装不能完全并行。

- **仍开放（Muse）：** 会话中途撤销角色、版本交集为空时的交互、大载荷用引用还是 blob，仍在别处待 review，本次通话不定。

### 方案评注（是否最优／权衡／开放风险）
- **近端是否合理最优：** 是。这是务实的混合：lease closer，需要时再分片扇出，最后串行组装。比 N 路一起抢写 Git 合适，也比钉死一个永久领袖合适。
- **权衡：** 心跳不稳时 lease 会来回倒手；分片边界切不好时，跨引用会掉进选错的分区；规模再大，顶层 closer 会成为瓶颈；把系统故障和单纯负载重分开，本身就有复杂度。
- **定稿前应先做原型：** lease 续租与移交的分类器；跨引用事件如何分到同一片；合成 100–1000 个参与方负载下，最终组装的吞吐；以及一条 agent 无法篡改的系统节点合并路径。
